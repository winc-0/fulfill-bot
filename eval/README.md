# 会话级评测

单句意图分类的准确率说明不了客服系统好不好用——用户是连着说好几轮的。这里测的是**整段会话**：每一轮的意图路由对不对、末了事情办成没有、该说的话说了没有、不该说的话有没有冒出来。

## 怎么跑

```bash
# 全量：llm + rule 两个变体，生成报告
python -m eval.run_eval

# 只跑一个变体
python -m eval.run_eval --variant llm

# 只跑某几段（改完代码定位回归用）
python -m eval.run_eval --only s06,s09,s10

# 冒烟前 5 段
python -m eval.run_eval --limit 5

# 指定输出目录（默认按时间戳）
python -m eval.run_eval --run-id final
```

前提：**模拟中台要在跑**（`python -m scripts.dev`，或单独 `python -m services.commerce.app`），否则所有动作都会失败。评测会自己重置对话状态，不需要手动清库。

产出在 `eval/results/<run_id>/`：

- `report.md` —— 总表 + 分组 + 失败明细（含每轮的实际动作、置信度、来源、回复片段）
- `llm.json` / `rule.json` —— 逐段逐轮的结构化记录

## 两个变体

| 变体 | 做法 | 测什么 |
|---|---|---|
| `llm` | qwen-flash 规划意图 | 系统正常状态下的能力上限 |
| `rule` | 把 `LLM_API_KEY` 置空，强制走规则规划器 | 模型超时/限流/没配 key 时的下限保障 |

两个变体共用同一条下游链路（校验、状态机、动作、知识检索），**只有"这句话想干什么"的判断方式不同**。所以两者的差距就只反映在"理解"上，干净可比。

## 脚本格式

`eval/sessions.jsonl`，一行一段会话：

```json
{
  "id": "s10",
  "group": "coreference",
  "sender_id": "c1001",
  "turns": [
    {"text": "帮我查下 YD20260410001 到哪了"},
    {"text": "运单号是多少"}
  ],
  "expect": {
    "turns": [
      {"action": "start", "flow": "tracking_query"},
      {"action": "answer"}
    ],
    "final": {"contains_any": ["YD20260410001"]}
  }
}
```

- `turns[].object`：模拟用户点了运单卡片，字段同前端传的 `{type, id, title, attributes}`。
- 每段会话前会用新 `sender_id` 起一个新档案，并把中台的理赔/改址/催派写表恢复种子状态——否则上一段提交的理赔会让这一段撞 409。

**逐轮断言**（`expect.turns[i]`）

| 字段 | 含义 |
|---|---|
| `action` | `start/cancel/resume/answer/handoff/chitchat/clarify`，可写成列表表示"都算对" |
| `flow` | 期望的流程 id，同样可写列表 |
| `paused_contains` | 期望这一轮把某个流程挂起。**判的是这一轮的 `transitions` 里有没有 `xxx:active->paused`**——不能看"当前挂起列表"，因为整段会话跑完后它可能已经被后面的恢复动作清空了（这是第一版踩过的坑） |

**末态断言**（`expect.final`）

| 字段 | 含义 |
|---|---|
| `contains_any` | 所有机器人回复拼起来，**命中任一**即可（注意：不是"每个都要有"） |
| `not_contains` | 这些词一个都不许出现（用来测"别把闲聊答成业务"） |
| `slots` | 末态槽位，会合并 active 任务与挂起任务的槽位 |
| `active_flow` | 末态正在进行的流程 |
| `handoff` | 末态转人工标志位 |

## 十一个分组

| 分组 | 段数 | 考察点 |
|---|---|---|
| `single_turn` | 3 | 一句话说清单号 + 意图，能否一次办成 |
| `slot_filling` | 3 | 分多轮补齐运单号、异常原因 |
| `coreference` | 3 | "那这个能赔吗""运单号是多少"这类指代 |
| `interrupt_resume` | 3 | 办到一半插队，之后"继续刚才的" |
| `cancel` | 3 | "算了不办了"之后不许再催 |
| `business_failure` | 3 | 运单不存在、重复理赔 409、仓库备货无轨迹 |
| `policy` | 3 | 纯规则问题走知识轨道，不许误当操作 |
| `handoff` | 2 | 明确要人工、情绪激烈 |
| `clarify` | 3 | 无关请求、含混说法，该澄清就澄清 |
| `object` | 2 | 用户点卡片进入，还有"这个"的指代承接 |
| `delivery` | 2 | 催派送成/败两路（可催 / 已妥投不该催） |

## 指标

| 指标 | 定义 |
|---|---|
| 会话完成率 | 该段会话的所有逐轮断言 + 末态断言全过，才算成功。**主指标** |
| 轨道路由准确率 | 只看 `action` 断言，逐轮统计 |
| 平均每轮耗时 | 会话总耗时 / 轮数 |
| 误转人工 | 非 `handoff` 分组的会话，末态却置了转人工位。**按状态位判定，不按回复文本**——模型会把兜底话术改写成"帮你转接人工"，那只是话术 |

## 加一段新脚本

1. 在 `sessions.jsonl` 末尾加一行，`id` 顺延（`s31`），选一个已有 `group` 或新开；
2. 先只写 `turns` 和 `expect.turns[].action`，跑 `--only s31` 看实际行为；
3. 确认行为合理之后再补 `flow`、`final` 断言——**别照着当前输出写断言**，那样等于自己给自己判卷。

反过来的情况也有：如果断言和实际不符，先分清是**系统答错**还是**脚本写错**。第一版评测里 6 处失败有 2 处是脚本的错（一段漏写了异常原因却要求出现"理赔单号"；一段把"当轮挂起"写成了末态检查），改脚本不是作弊，把判断依据写清楚就行。

后来又改了澄清组的 2 条末态断言，同样属于口径过期而不是系统回退：一条断言"闲聊回复里不许出现运单号"（电商口径下的判据，物流口径下闲聊本来就该引导用户报运单号），另一条用 `contains_any` 去匹配模型自由发挥的拒绝话术（换一种说法就误判）。两条都改成"不许出现真实业务数据 + 末态不得有进行中流程 / 转人工位"——判状态位而不是判措辞。

## 局限

- 30 段是自建小样本，跑满只说明回归守住了，不代表能力被证明。样本外的说法（方言、错别字、"一句话三个意图"）照样会漏。
- 断言的期望值是作者定的，带着作者对"怎么答才算对"的偏好。比如"取消后又说继续"这一段，`resume` 和"重新发起"都算对——取消的任务本来就不在挂起列表里。
- 耗时含真实模型调用，受网络影响，只能横向看两个变体的相对差距。
