# 履约客服助手 Fulfill-Bot · 任务型多轮客服 Agent

一个能**真正把事情办完**的仓配履约客服助手：查运单、改派送地址、催派送、异常件理赔、答服务规则，用户中途插话、改主意、反悔，它都记得住。

不是"问一句答一句"的问答机器人，而是一套把**多轮任务状态**管住的对话系统。

> 同系列三个项目覆盖企业 LLM 落地的三类场景：
> **履约知识助手 Warehouse-KB** 管文档（RAG 检索问答）、**仓配自助问数 LogiQL** 管数据（NL2SQL 问数）、**履约客服助手 Fulfill-Bot** 管动作（任务型多轮对话）。

---

## 为什么这个比"接个大模型"难

政策问答只要检索准就行；让系统替用户**把事办完**，难的是状态：

| 场景 | 天真做法会怎样 | 这里的做法 |
|---|---|---|
| 用户报异常件说到一半去查另一张运单 | 理赔流程被覆盖，回来还得重说 | 旧任务挂起，保留步骤与已填槽位；说"继续"从断点接着跑 |
| 用户说"算了不理赔了" | 后面还继续催理赔原因 | 取消后立刻终止，不再念台词 |
| 用户问"那这单还能改地址吗" | 检索不到"这单"是什么 | 把当前聚焦运单拼进检索查询 |
| 用户问"运单号是多少" | 当服务规则问题去知识库里搜，答不上来 | 识别为"问当前这单的字段"，改派运单流程重新取数 |
| 模型要把运单号抄成别的 | 打到中台 404 | 运单号只认用户原话与已知槽位，模型写错就纠正 |
| 拦截接口返回 409（运单已出库） | 照样回复"已拦截成功" | 动作失败**必须终止流程**，绝不念成功模板 |
| 模型编一个不存在的流程 | 照着幻觉往下执行 | 配置里没有的流程/槽位一律拦掉，降级成澄清 |

## 六个设计决定

**1. 一次 turn 固定四步，状态只在引擎里改**
规划 → 校验 → 调度 → 推进。规划和动作是纯函数，所有状态变更集中在 `engine.py`。
好处直白："中断后恢复"只需要读回一个 `step_id`，不用去各处拼上下文。

**2. 流程写在 YAML 里，不在代码里**
```yaml
claim_request:
  steps:
    - {id: start, type: start, next: ask_tracking_number}
    - {id: ask_tracking_number, type: collect, slot_name: tracking_number,
       response: {text: "可以，请告诉我需要报异常的那张运单号。"}, next: verify}
    - {id: verify, type: action, action: action_lookup_shipment_status, next: ask_reason}
    - {id: ask_reason, type: collect, slot_name: claim_reason,
       response: {text: "请简单说一下异常情况和损失，方便定责理赔。"}, next: submit}
    - {id: submit, type: action, action: action_submit_claim, next: respond}
    - {id: end, type: end, next: []}
```
改话术、加一步、换判断条件都不用改代码。加载期会做引用完整性校验（`next` 指向的步骤存在、`collect` 的槽位已定义、`action` 已注册），配置写错直接 `FlowConfigError`，不会上线后才炸。

**3. 中断 = 挂起，不是丢弃**
`pause_active()` 把当前任务连同 `step_id` 和已填槽位压进 `paused_tasks`（上限 3 个，同流程去重）。用户说"继续刚才那笔理赔"，从断点续跑，不重头问一遍。
理赔原因这类**任务域槽位**（`TASK_SCOPED_SLOTS`）不参与跨任务补槽——否则"上一单的问题"会被填进这一单。

**4. 防幻觉是校验层的事，不是靠 prompt 求模型**
四层，任何一层不过就降级成澄清而不是报错：
- `flow` 必须存在于 YAML；
- 槽位必须已定义，模型塞的野字段丢掉；
- 状态自洽（没挂起任务不能 resume、没进行中任务不能 cancel）；
- 运单号只认两个来源：**用户原话**、**已知槽位**。模型自己写的一律不认。
- 理赔原因 / 新地址这类自由文本槽位，只认"**正在追问它**"或"**这句话里逐字说过且运单号已知**"。没有形状可校验的东西，不能再让模型替用户作答。

反过来也有"修复而非丢弃"的三条：模型把流程名填进 `action` 字段 → 认出来改派；`answer` 却带着运单号 → 改派运单咨询；`answer` 却在问当前这单的派送字段 → 改派运单查询。

**5. 三条轨道靠"能不能落到具体对象"来分**
- 带运单号、或承接上一轮追问 → **Task**（走 YAML 流程，取的是真数据）
- 纯规则问题（"破损件的赔付标准是什么"）→ **Knowledge**（字符二元组 + IDF 加权 + 标题覆盖 + 同义扩展）
- 寒暄/无关 → **ChitChat**

知识检索故意不用向量库：语料就几页，字符二元组可解释——能直接说清命中了哪一段、得分多少。真到几百篇再换，接口不用动。

**6. 写操作失败必须终止**
动作返回 `ActionResult(ok=False, abort=True)`，引擎立刻结束任务并把失败原因说成人话。
409 单独处理："这张运单已经有一笔理赔在审核里了"——不是"提交失败，请重试"。

## 会话级评测

不是"单句意图分类准确率"，而是**整段会话跑通没有**：建了 30 段多轮脚本、分 11 组（单轮查询 / 多轮补槽 / 指代消解 / 中断恢复 / 中途取消 / 业务失败 / 规则问答 / 转人工 / 澄清兜底 / 对象卡片 / 催派送），每段逐轮断言 `action`、`flow` 和末态槽位，另外断言回复里该出现/不该出现的内容。

两个变体对照：`llm` 用 qwen-flash 规划；`rule` 把 API Key 置空，强制走规则规划器（同一条下游链路，只换大脑）。

| 指标 | llm | rule |
|---|---|---|
| 会话完成率 | 100.0%（30/30） | 100.0%（30/30） |
| 轨道路由准确率 | 100.0%（53/53） | 100.0%（53/53） |
| 平均每轮耗时 | 1.5~1.6 s | 0.4~0.5 s |
| 误转人工 | 0/28 | 0/28 |

| 分组 | 段数 | llm | rule |
|---|---|---|---|
| 单轮查询 `single_turn` | 3 | 3/3 | 3/3 |
| 多轮补槽 `slot_filling` | 3 | 3/3 | 3/3 |
| 指代消解 `coreference` | 3 | 3/3 | 3/3 |
| 中断恢复 `interrupt_resume` | 3 | 3/3 | 3/3 |
| 中途取消 `cancel` | 3 | 3/3 | 3/3 |
| 业务失败 `business_failure` | 3 | 3/3 | 3/3 |
| 规则问答 `policy` | 3 | 3/3 | 3/3 |
| 转人工 `handoff` | 2 | 2/2 | 2/2 |
| 澄清兜底 `clarify` | 3 | 3/3 | 3/3 |
| 对象卡片 `object` | 2 | 2/2 | 2/2 |
| 催派送 `delivery` | 2 | 2/2 | 2/2 |

**这张 100% 该怎么读**：
- 首轮跑出来是 **llm 80%（24/30）、rule 66.7%（20/30）**。剩下 6 处里，**2 处是脚本自己写错**（漏了一轮理赔原因、把"末态是否有挂起任务"当成"当轮是否挂起"来断言），其余 4 处是真缺陷，逐个修完才到 100%：
  - 模型把 `YD20260410001` 抄成 `YD2026041001` → 加运单号一致性校验；
  - "运单号是多少"被当成服务规则问答 → 加运单字段改派；
  - 兜底话术的"按原因分支"其实是死代码（`context.get('reason')` 一直读到空字典）→ 修参数传递；
  - 检索把"包裹破损怎么赔"判给了"保价规则" → 换 IDF 加权 + 标题覆盖。
- 30 段是自建小样本，跑 100% 说明**回归守住了**，不等于能力已被证明。样本里没有的刁钻说法（方言、错别字连篇、一句话三个意图）照样会漏。
- **100% 之后仍然被抓出四个 bug**，是靠手动演示和重复跑评测（不是靠脚本本身）：用户说"那这单能理赔吗"被模型判成要报案、接着就问"异常情况是什么"；用户说"直接帮我报异常"整句被当成理赔原因，还真提交上去了；理赔办到一半插队查另一张运单，查单的运单号串进了挂起的理赔任务，回来把**另一单**给赔了；以及最近这个——用户只说"包裹破损了，我要报异常"，模型就把理赔原因填成"破损"，等下一轮用户刚报完运单号，流程跳过 `ask_reason` 直接提交，理赔单上写的是模型替用户编的原因。四个都补了护栏与回归测试（单测 58 → 67）。
  - 第三个是这批里最值钱的教训：`remember_slot()` 会写进"当时的 active_task"，而代码是先写槽位、后挂起旧任务——顺序反了。这类 bug 在脚本里很难撞上，得靠"演一遍给真人看"。
  - 第四个是**靠重复跑评测**抓到的：`rule` 变体次次 30/30，`llm` 变体却在 29/30 和 30/30 之间跳。差距不在脚本而在模型——同一句话它这轮决定自己填原因、下轮决定不填。修法是在校验层加一条硬规则（任务域自由文本槽位只认"正在追问它"或"这句话里逐字说过且运单号已知"），把"模型的心情"变成"代码的判据"。
  - 结论：**评测保证不回退，演示负责发现"脚本想不到的事"，重复跑负责发现"模型时灵时不灵"，三件事都得做。**
- `rule` 变体能追平，是因为两者共用同一条下游链路，差别只在"这句话想干什么"。语料越复杂、说法越绕，差距会拉开——这也是为什么规则规划器要保留：它是模型超时/限流时的下限保障。
- **误转人工在 0~1 之间浮动**，取决于模型那一轮给"帮我订一张去上海的高铁票"（能力外的需求）选了 `handoff` 还是老实说"这个我暂时接不了"。前者体验更好，但按"不该转的转了"这一口径记一次误转——两种处理都说得过去，记在这里不藏。
- 澄清组的两条末态断言已经从"回复里不许出现运单号"改成"不许出现真实业务数据 + 末态不得有进行中流程 / 转人工位"。前者在物流场景下并不成立——闲聊本来就该引导用户报运单号，拿它当判据是拿口径当结论；后者才是"别把闲聊答成业务"的真正含义。

复现方式见 [`eval/README.md`](eval/README.md)。

## 快速开始

```bash
# 1. 依赖（Python 3.11 / 3.12，本项目在 3.12 上验证）
python -m venv .venv
.venv/Scripts/activate          # Windows；macOS/Linux 用 source .venv/bin/activate
pip install -e .

# 2. 配置：只填 LLM_API_KEY 就能跑；不填也能跑（自动回落规则规划器）
cp .env.example .env

# 3. 一键起三个服务（自动建库、灌种子数据、体检）
python -m scripts.dev
```

## 已知限制

- **会话状态存 SQLite**，单机够用；多实例部署需要换 Redis 并加分布式锁，否则同一用户的两条消息会打架。
- **规划器每轮调一次模型**（约 1.6 s/轮）。要更快可以把常见句式前置成规则，或改成小模型 + 缓存；`planner_model` 已独立配置，不影响写作模型。
- **知识检索是词面匹配**，同义改写的说法（"东西坏了咋整"）要靠 `EXPANSIONS` 手工补，不是语义检索。几百篇以上应换向量库。
- **中台是模拟的**，接口按真实履约系统的常见形态设计（统一 `{code,message,data}`、409 表示状态冲突），但没有对接过真实 WMS / TMS，鉴权/限流/幂等都没做。
- **`/api/chat/tts` 返回 501**，语音是留的壳。
- 评测脚本 30 段偏少，且是自己出题自己答，标准答案里带着作者的偏好。
